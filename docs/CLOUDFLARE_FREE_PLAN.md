# SIGMA CAR on Cloudflare Free (Pages Free + Workers Free + D1 Free)

Audit, changes, tests and a PowerShell deployment guide for running the API at **no cost**. There is no Workers
Paid plan, no card and no paid service. Measured on 2026-11-14 in local `workerd` / Miniflare (Wrangler 4.154.0) and
with the Worker handler under Node. **Nothing was deployed.**

## 1. Verdict

| Area | On Free | Evidence |
|---|---|---|
| Catalog, filters, comparison data, vehicle detail, related | ✅ fits | 1 D1 query, 1 row read, ≈ 1–3 ms CPU (estimate) per request |
| AR manifests (all vehicles) | ✅ fits | ≈ 2–3 ms; same manifest as the Pages static snapshots |
| Cart, checkout, orders, payments (sandbox), admin pages, analytics, CMS, media | ✅ fits | 1–3 D1 queries, ≈ 1–5 ms (warm). The first call of a code path in a new isolate can take longer (cold JIT; e.g. analytics overview 15 ms once, 1.8 ms warm) |
| Static site, 3D models, AR files | ✅ free and unlimited | Pages serves them without invoking Functions (`_routes.json` generated by Wrangler: `include: ["/api/v1/*"]`) |
| **Login, registration, password change, admin "create user"** | ⚠️ **over the 10 ms budget — must be verified on Cloudflare** | scrypt password hashing: 33–48 ms CPU per hash in `workerd` on this machine; 45–69 ms per request (estimate); password change hashes twice |
| D1 persistence, quotas | ✅ fits a course demo | per request: 1 row read (steady state); per write: ≈ 3–10 rows plus index rows (100,000 rows written/day allowed) |
| Live SMTP e-mail | ➖ unverified (any plan) | use the default sandbox queue or an HTTP e-mail webhook |
| USDZ files > 25 MiB | ➖ Pages file limit (any plan) | converted on the iPhone/iPad, as before |

**The application runs on Free except for one item that cannot be decided locally.** The 4 endpoints that hash
passwords need about 4–5× the documented 10 ms CPU. Cloudflare says each isolate has "built-in flexibility to allow
for cases where your Worker infrequently runs over the configured limit" (Workers limits page), but gives no number.
Whether occasional logins stay within that flexibility can only be measured on Cloudflare (§6, step 7).
Full compatibility is **not** claimed.

## 2. Free plan limits that apply

| Limit (Free) | Value | Source |
|---|---|---|
| CPU per HTTP request | 10 ms; I/O waits (D1, fetch) do not count; error 1102 when consistently exceeded | Workers limits |
| Requests | 100,000 / day (Workers + Pages Functions), reset 00:00 UTC; error 1027 | Workers limits |
| Startup (global scope) | 1 s | Workers limits |
| Memory | 128 MB per isolate | Workers limits |
| Worker size | 64 MiB uncompressed | Workers limits |
| D1 queries per invocation | 50 (a `batch()` counts as 1) | D1 limits |
| D1 rows read / written | 5,000,000 / 100,000 per day; full scans count every scanned row; index updates count as extra rows written | D1 pricing |
| D1 storage | 500 MB per database, 5 GB total | D1 limits / pricing |
| Static assets on Pages | free, not counted as Functions requests when outside `_routes.json` | Pages |

## 3. Audit (Phase 1)

| # | Question | Finding |
|---|---|---|
| 1 | Requests over 10 ms CPU | Only the 4 scrypt endpoints (≈ 45–69 ms). The first request of a new isolate was ≈ 23 ms in Node, mostly Node's own lazy loading; in `workerd` the module evaluation now happens at startup (≈ 32 ms of the 1 s startup budget, measured with `wrangler check startup`). Dev seeding on an empty database hashes 3 passwords (≈ 150 ms), so it must stay off remotely (it is: `SIGMACAR_ALLOW_DEV_SEED=false`). |
| 2 | Password hashing | scrypt N=16384, r=8, p=1, 64-byte key. It is already below the OWASP minimum for scrypt, so it **must not be weakened**. Any secure password hash is slow by design; no secure option fits in 10 ms. |
| 3 | D1 queries / storage | ≤ 3 queries per request (limit 50). Before this change, a reload after another isolate's write re-read **whole collections** (e.g. every analytics event); now only changed rows (§4). Dataset ≈ 0.2 MB. |
| 4 | Memory / requests | State in memory ≈ 0.2 MB; bundle 2.4 MB. Each API call = 1 Pages Function invocation + 1 Worker invocation. Plan for **≈ 50,000 API calls/day** to be safe (whether a service-binding call counts separately is not stated in the limits page). |
| 5 | Unsupported Node APIs | None on the request path (see `CLOUDFLARE_WORKERS_COMPATIBILITY.md`); SMTP over `node:tls` remains unverified. |
| 6 | Other blockers | No paid-only settings in `wrangler.api.toml` (checked by a test). D1, service bindings, Workers Logs (`[observability]`) and Durable Objects (SQLite) are all available on Free. |

## 4. Changes made (Phase 2) — behaviour unchanged

| Change | Why | File |
|---|---|---|
| Gemini SDK loaded on first Gemini call | `ai-service` loaded in 183 → 35 ms; nothing changes when Gemini is used | `backend/application/ai-service.js` |
| Backend evaluated at Worker startup | moves module evaluation out of the first request's 10 ms into the 1 s startup budget; a configuration error is now remembered for the isolate (a half-initialised bundled module can never be reused by a later request) | `backend/cloudflare/worker.mjs`, `runtime.js` |
| Random values created on first use, not at module load | needed for the startup preload: Workers forbid random values in global scope. The first attempt failed in `workerd` (`Disallowed operation called within global scope`) because of the outbox worker id and the development-only ephemeral JWT secret. The values and their lifetime are unchanged. | `backend/workers/outbox-worker.js`, `backend/config/index.js` |
| Incremental sync (migration `0002`) | rows carry the commit revision; deletions are recorded. An isolate that is behind reads only rows with `rev >` its own (indexed): CPU and D1 rows read ∝ changes, not collection size. Unchanged records keep their in-memory objects. | `backend/infrastructure/d1/migrations/0002_incremental_sync.sql`, `persistence/d1-state-store.js` |
| One fewer write per commit | the per-collection revision row is no longer needed | `d1-state-store.js` |
| Import tool / admin bootstrap stamp the revision | running isolates pick imported rows up incrementally | `scripts/d1/*.js` |

**Not changed:**

- password hashing (a test now asserts N=16384, r=8, p=1, a 64-byte key and a 16-byte salt);
- API contracts, the frontend, AR, and the 32 business modules.

## 5. Tests (Phase 3)

| Command | Result |
|---|---|
| `npm test` (incl. new `tests/unit/workers_free_plan.test.js`) | **280 / 280 pass** |
| `npm run test:worker-runtime` | 80 pass, 1 skipped (JSON-disk test), 0 fail |
| `npm run test:workers` | **7 / 7** in `workerd` (contract 83/85 identical + 2 documented differences, concurrency, rollback drill) |
| `npm run test:e2e` | 19 / 19 (frontend and AR unchanged) |

`tests/unit/workers_free_plan.test.js` runs the Worker handler against an imported database and measures every
request: D1 queries, rows read and written, and a CPU estimate. It covers login, registration, catalog, comparison
data, orders, admin, D1 persistence, routing and AR manifests. It asserts:

- ≤ 50 D1 queries per request;
- 1 row read per steady-state request;
- read-only endpoints write nothing;
- startup does not touch D1;
- no paid-only settings;
- hashing strength unchanged.

With `WORKERS_FREE_CPU_STRICT=1` it also fails on any non-hashing request above 10 ms. That option is off by
default because CPU timing depends on the machine.

## 6. Deployment guide — Free plan (Phase 4), Windows PowerShell

Run everything from the repository root after `npm ci`. Wrangler is pinned (4.154.0); use `npx.cmd`.
**Production bindings of the `sigma-car` Pages project are not touched until §8, which needs explicit approval.**
Steps 1–7 use a separate Worker (`sigmacar-api-staging`) and the Pages **Preview** environment.

1. **Log in (free account; no billing needed)**
   ```powershell
   npx.cmd wrangler login
   npx.cmd wrangler whoami
   ```
2. **Create the D1 database (free) and paste its id** into `wrangler.api.toml` → `[[env.staging.d1_databases]]`,
   replacing `REPLACE-WITH-STAGING-D1-DATABASE-ID`.
   ```powershell
   npx.cmd wrangler d1 create sigmacar-staging
   npx.cmd wrangler d1 migrations apply DB --env staging --remote -c wrangler.api.toml     # applies 0001 and 0002
   ```
3. **Secrets**
   ```powershell
   node -e "process.stdout.write(require('crypto').randomBytes(48).toString('base64url'))" | npx.cmd wrangler secret put JWT_SECRET --env staging -c wrangler.api.toml
   node -e "process.stdout.write(require('crypto').randomBytes(32).toString('hex'))" | npx.cmd wrangler secret put PAYMENT_WEBHOOK_SECRET --env staging -c wrangler.api.toml
   $s = node -e "process.stdout.write(require('crypto').randomBytes(48).toString('base64url'))"
   $s | npx.cmd wrangler secret put PROXY_SHARED_SECRET --env staging -c wrangler.api.toml
   Set-Clipboard -Value $s; Remove-Variable s     # paste into Pages → Preview → SIGMA_PROXY_SHARED_SECRET (step 5)
   ```
4. **Data.** Import precomputed hashes; never use the dev seed remotely, because it hashes 3 passwords in one
   request.
   ```powershell
   node scripts/d1/json-to-d1.js --execute --env staging --catalog-only --exclude-demo-accounts --report docs/D1_DATA_MIGRATION_REPORT_staging.md
   $env:SIGMA_ADMIN_PASSWORD = '<long admin password>'
   node scripts/d1/create-admin.js --email <admin e-mail> --name "<name>" --env staging
   Remove-Item Env:SIGMA_ADMIN_PASSWORD
   ```
   For a course demo that needs the sample orders and reviews, the full snapshot can be imported instead (without
   `--catalog-only --exclude-demo-accounts`). It then contains the **demo accounts with public passwords**; only do
   this for a short-lived demo.
5. **Deploy the Worker, then connect the Pages Preview environment**
   ```powershell
   npx.cmd wrangler deploy --env staging -c wrangler.api.toml
   ```
   In the dashboard, go to **Workers & Pages → sigma-car → Settings → Bindings → Preview → Add → Service binding**,
   and set variable `SIGMA_API` to service `sigmacar-api-staging`. Then, under **Variables and Secrets → Preview**,
   add `SIGMA_PROXY_SHARED_SECRET` with the value from step 3.
6. **Deploy a preview of the site** (this does not change production):
   ```powershell
   npm run build
   npx.cmd wrangler pages deploy dist --project-name sigma-car --branch staging
   $B = '<preview URL printed above>'
   Invoke-RestMethod "$B/api/v1/health"                      # storageMode must be "d1"
   Invoke-RestMethod "$B/api/v1/vehicles" | Select-Object -ExpandProperty data | Measure-Object
   Invoke-RestMethod "$B/api/v1/vehicles/tesla-cybertruck/ar-manifest" | Select-Object -ExpandProperty data | Select-Object vehicleId, schemaVersion
   ```
7. **Verify the CPU-heavy endpoints on Free.** This is the deciding test. Open a second window with
   `npx.cmd wrangler tail sigmacar-api-staging --format pretty`, then run:
   ```powershell
   $body = @{ email = '<admin e-mail>'; password = '<password>' } | ConvertTo-Json
   $ok = 0; $fail = 0
   1..20 | ForEach-Object {
     try { Invoke-RestMethod "$B/api/v1/auth/login" -Method Post -ContentType 'application/json' -Body $body | Out-Null; $ok++ }
     catch { $fail++; Write-Host "attempt $_ failed: $($_.Exception.Message)" }
     Start-Sleep -Seconds 3
   }
   "logins ok=$ok failed=$fail"
   ```
   - **Pass:** 20/20, and `wrangler tail` shows no `exceededCpu` outcome.
   - Also check **Workers & Pages → sigmacar-api-staging → Metrics → CPU time** (median and p99).
   - Repeat for registration on the preview site.
   - If logins fail with `exceededCpu`, go to §7.
8. **Production (only with explicit approval).** Repeat steps 2–5 with `--env production` (database
   `sigmacar-production`, new secrets, `--confirm-production` for the two scripts). Then add the
   **Production** binding `SIGMA_API → sigmacar-api` in the Pages project and run
   `npx.cmd wrangler pages deploy dist --project-name sigma-car`. Rollback: remove the binding
   (`CLOUDFLARE_WORKERS_ROLLBACK.md` §1).

Daily usage stays free as long as API calls stay under the quotas in §2. When a quota is exceeded, the API returns
errors until 00:00 UTC; nothing is charged.

## 7. If password hashing exceeds the Free CPU budget

All options below are free. None weakens the hash.

| Option | Effort | Notes |
|---|---|---|
| **A. Accept and retry.** Logins are rare in a demo; a request ended by the CPU limit returns a JSON 502 from the Pages Function and the user can retry. | none | Works only if overruns are rare (step 7 measures this). |
| **B. Hash in a Durable Object** (SQLite Durable Objects are available on Free) | small: one class wrapping `Security.hashPassword` / `verifyPassword`, called from the 4 endpoints | Cloudflare does not document a different CPU limit for Durable Objects on Free (the limits page defers to the Workers limits). **Must be tested on Cloudflare before relying on it**, the same way as step 7. |
| **C. Demo-day fallback: previous architecture through a free Cloudflare Tunnel.** `node server.js` on a PC + `cloudflared tunnel --url http://localhost:3000` (`run_cloudflare.bat`), and set `SIGMA_BACKEND_ORIGIN` on the Pages Preview environment. | none (already built) | Free; the PC must stay on during the demo; data in the local JSON file (`--export-json` moves D1 data there). |

Lowering the scrypt parameters or switching to a fast hash would fit in 10 ms. That **weakens password security** and
is deliberately not offered.

## 8. What the Free plan cannot guarantee

- **Hashing within 10 ms CPU:** login, registration, password change and admin user creation need more (see §1 and
  §7); not verified on Cloudflare.
- **Daily quotas:** 100,000 requests and 100,000 D1 rows written per day. A heavy load test or crawler can exhaust
  them; the API then fails until 00:00 UTC.
- **Cold starts:** the first request of a new isolate reads the whole dataset (≈ 220 rows today) and runs cold code
  paths. Larger datasets (e.g. tens of thousands of analytics events) make that first request heavier.
- **Unchanged limits (any plan):** live SMTP from Workers (unverified), and USDZ files > 25 MiB (on-device conversion
  on Pages).
